# source-command-commit-push

Use this skill when the user asks to run the migrated source command `commit-push`.

## Command Template

현재 워크트리(스테이징/언스테이징/untracked 포함)의 변경 사항을 검토해 논리적 단위로 나눠 커밋하고, 바로 푸시까지 한다.

인자: (선택) 커밋 범위 힌트. 없으면 `git status`의 모든 변경을 대상으로 한다.

## test-commit과의 차이

- `test-commit`은 Playwright E2E까지 돌리고 **푸시는 하지 않는다**.
- 이 명령은 tsc/lint + **빌드 부팅 확인**까지만 하고 **바로 push까지** 수행한다. E2E는 사용자가 직접 브라우저로 확인 중이거나 별도로 몰아 돌릴 계획일 때 쓰는, 그보다 가벼운 경로다.
- E2E/브라우저 검증이 필요한 상황이면 이 명령 대신 `test-commit`을 쓰거나, 사용자에게 먼저 확인한다.

## 전제

이 명령은 대화 맥락 없이 콜드로 호출되는 경우가 많다 — 다른 세션이나 Codex 등 별도 에이전트가 작업해놓은 결과를 대신 커밋·푸시해주는 용도이기 때문이다. "누가 왜 이 변경을 했는지"는 알 수 없고 알 필요도 없다. **판단 근거는 오직 `git status`/`git diff`/`git log`뿐**이며, 무엇을 커밋할지는 지금 워크트리에 있는 변경 전체를 그대로 범위로 삼는다(인자로 힌트가 있으면 그것도 참고).

**빌드 부팅 확인을 위해 이 명령은 `pnpm start`로 3000번 포트를 잠깐 점유한다.** AGENTS.md의 "dev 서버 임의 종료·재시작 금지" 규칙에 대한 의도적 예외이며, 아래 3단계에서만 적용된다 — 사용자가 이 명령을 부르기 전에 다른 세션의 `pnpm dev`를 직접 꺼두는 것을 전제로 한다.

## 핵심 정책

1. **워크트리에 있는 변경 전체를 범위로 삼는다.** 별도 대화 맥락과 대조하지 않는다 — 다만 diff 자체를 봤을 때 이상해 보이는 것(설명 없이 섞인 것 같은 대규모/무관한 변경, 명백한 디버그 코드)이 있으면 멈추고 사용자에게 확인한다.
2. **논리적 관심사 단위로 커밋을 나눈다.** 같은 기능/화면을 건드리는 변경은 한 커밋으로 묶고, 서로 무관한 변경(예: SEO 정적화 vs 홈 위젯 리디자인)은 별도 커밋으로 분리한다. 전부 한 가지 관심사면 커밋 1개로 충분하다.
3. **신규 오류만 고친다.** tsc/lint/빌드에서 이번 변경으로 새로 생긴 오류만 대응하고, 기존부터 있던 오류는 건드리지 않는다.
4. **다른 프로세스를 임의로 종료하지 않는다.** 검증 자동화가 사용자나 다른 세션의 작업 환경을 깨서는 안 된다. 3000번 포트가 이미 점유돼 있으면(다른 세션의 dev 서버일 수 있다) 거기서 멈추고 사용자에게 "3000번 포트를 정리해달라"고 요청한 뒤 재개를 기다린다. 이 명령이 직접 띄운 `pnpm start` 프로세스만 스스로 종료 대상이다. (`test-commit`과 동일 정책)
5. **기본 브랜치(main)에서는 직접 커밋·푸시하지 않는다.** main이라면 **커밋을 시작하기 전에** 사용자에게 알리고, 작업 브랜치를 만들지·브랜치명을 뭘로 할지 확인한 뒤 진행한다. 브랜치명은 임의로 정하지 않는다 — 이 명령의 "워크트리만 보고 기계적으로 처리한다"는 성격을 벗어나는 판단이기 때문. feature 브랜치(main이 아닌 브랜치)면 커밋·push 모두 바로 진행한다. (`test-commit`과 동일 정책)
6. **push가 non-fast-forward 등으로 거부되면 그 자리에서 멈춘다.** `--force`로 우회하지 않는다. 원격에 새 커밋이 있다는 뜻이므로 사용자에게 상황을 보고하고 지시를 받는다.
7. **Codex 저작자 표시를 항상 포함한다.** 커밋 메시지 끝에 `Co-Authored-By`와 `Codex-Session` 줄(현재 세션 시스템 지침에 명시된 값)을 그대로 붙인다.

## 절차

### 1단계 — 변경 파악 및 분할 계획
- `git status`와 `git diff`(untracked는 내용도 확인)로 전체 변경을 읽는다.
- 변경 파일 중 다음이 섞여 있으면 사용자에게 먼저 알리고 진행 여부를 확인한다(있어도 되지만 눈에 띄게 짚고 넘어간다):
  - `package.json`/lockfile, `next.config.*`, `tsconfig.json`, 미들웨어(`proxy.ts` 등), `.github/workflows/*`, `.env*`
  - `.env`, `*.pem`, `*key*`, `*secret*`, `*credential*` 등 이름만으로 민감정보가 의심되는 파일, 또는 diff 내용에 `AKIA`, `-----BEGIN`, `SECRET=`, `PASSWORD=` 같은 패턴
- 관심사별로 묶어 커밋 개수와 각 커밋에 포함할 파일을 정한다.

### 2단계 — 정적 검증 (AGENTS.md 작업 검증 규칙)
```
npx tsc --noEmit -p .
pnpm lint
```
- 신규 오류가 있으면 고치고 재검증. 못 고치면 중단하고 보고한다.

### 3단계 — 빌드 부팅 확인
1. 3000번 포트 점유 여부를 확인한다(`netstat -ano | findstr :3000` 등). 점유돼 있으면 **여기서 멈추고** 사용자에게 다른 세션의 dev 서버를 꺼달라고 요청한 뒤 응답을 기다린다. 절대 그 프로세스를 대신 종료하지 않는다.
2. 포트가 비어 있으면 `pnpm build`를 실행한다. 실패하면 중단·보고(신규 오류만 대응, 2단계와 동일 기준).
3. 빌드 성공 시 `pnpm start`를 백그라운드로 띄우고, 정상 기동(로그의 Ready 신호 또는 `http://localhost:3000` 응답)을 짧은 타임아웃(예: 15~20초) 안에 확인한다.
4. 확인되면 **이 명령이 띄운 프로세스만** 즉시 종료한다.
5. 타임아웃/에러로 기동 확인에 실패하면 빌드 실패로 간주해 중단·보고한다.

### 4단계 — 커밋
- 계획한 단위대로 `git add <파일들>` 후, `git diff --cached`로 실제로 커밋될 내용을 한 번 더 확인한다(의도치 않게 딸려온 파일이 없는지).
- `git commit`으로 커밋한다. 메시지는 한국어, `feat:`/`fix:`/`chore:` 프리픽스, "무엇을 왜 바꿨는지" 위주로 작성한다. 최근 `git log --oneline`으로 톤을 맞추고, 끝에 Codex 저작자 표시를 붙인다.
- 남은 그룹이 있으면 반복한다.

### 5단계 — 푸시
- 현재 브랜치가 main이 아니면 `git push origin <현재 브랜치>`를 바로 실행한다.
- main이면 애초에 4단계 전에 확인을 받았어야 한다(핵심 정책 5).
- 거부되면(핵심 정책 6) 멈추고 보고한다.

### 6단계 — 결과 보고
- 만든 커밋 목록(`git log --oneline -N`)
- tsc/lint/빌드 부팅 확인 결과 한 줄 요약
- push 결과
- 커밋하지 않고 남겨둔 변경이 있으면 그 이유

## 출력 형식

- 분할 계획(커밋 # · 파일 · 메시지 요지) + 확인이 필요한 민감/인프라 파일 유무
- 정적 검증 + 빌드 부팅 확인 결과
- 최종 커밋 로그 + push 결과
