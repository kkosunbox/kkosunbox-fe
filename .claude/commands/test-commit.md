현재 작업 중인(스테이징/언스테이징/untracked 포함) 변경 사항을 **Playwright E2E 테스트로 검증한 뒤, task 단위로 나눠 여러 개의 커밋**으로 만든다.

인자: (선택) 커밋 범위 힌트나 task 분할 지시. 없으면 `git status`의 모든 변경을 대상으로 자동 분할한다.

## commit-push와의 관계

- 일반적인 변경(스타일/카피/단순 UI 조정 등 "빌드되고 뜨면 되는" 수준)은 `commit-push`가 더 가볍다 — tsc/lint + 빌드 부팅 확인 후 바로 push까지 한다.
- 이 명령은 **결제·인증·체크아웃처럼 동작 회귀가 실제로 걱정되는 변경**, 또는 브라우저로 직접 확인 못 한 변경에 쓴다. 빌드가 성공해도 결제 플로우가 깨졌는지는 알 수 없기 때문 — 그건 Playwright E2E만 잡아준다.
- 둘 중 뭘 써야 할지 애매하면 위험도가 더 높다고 보고 이 명령을 쓴다.
- **검증 범위는 이 명령이 commit-push를 포함한다.** `playwright.config.ts`의 webServer가 `pnpm build && pnpm start`(PORT 3001)이므로 `pnpm test`만 돌려도 빌드+부팅 확인이 이미 포함된다. 여기에 별도 빌드 단계를 추가하지 말 것.

## 핵심 정책

1. **테스트 실패 시 중단한다.** Playwright 테스트가 하나라도 실패하면 **커밋하지 않고** 실패 내용을 보고한 뒤 멈춘다. 사용자가 명시적으로 무시를 지시하지 않는 한 진행하지 않는다.
2. **요청 범위만 커밋한다.** 사용자가 만들지 않은/설명과 다른 변경을 발견하면 멈추고 보고한다 (CLAUDE.md 작업 범위 준수 규칙). 대화 맥락 없이 콜드로 불렸다면(다른 세션·Codex 작업분을 대신 커밋해주는 경우) 이 판단은 diff 자체가 봐도 이상한지(설명 없는 대규모/무관 변경, 민감정보로 보이는 파일·패턴, 명백한 디버그 코드)로 대신한다.
3. **기본 출력은 로컬 커밋까지다.** 원격 저장소는 변경하지 않는다 — push는 사용자가 명시적으로 요청한 경우에만 수행한다.
4. **기본 브랜치(main)에서는 직접 커밋하지 않는다.** main이라면 사용자에게 알리고 작업 브랜치를 만들지, 브랜치명을 뭘로 할지 확인한 뒤 진행한다. 브랜치명은 임의로 정하지 않는다 — 이 명령의 "워크트리만 보고 기계적으로 처리한다"는 성격을 벗어나는 판단이기 때문. (`commit-push`와 동일 정책)
5. **다른 프로세스를 임의로 종료하지 않는다.** 검증 자동화가 사용자나 다른 세션의 작업 환경을 깨서는 안 된다. 이 명령이 직접 띄운 프로세스만 스스로 종료 대상이다. (3단계 참고)
6. **커밋 메시지 끝에 Claude 저작자 표시를 항상 포함한다.** `Co-Authored-By`와 `Claude-Session` 줄(현재 세션 시스템 지침에 명시된 값)을 그대로 붙인다.

## 절차

### 1단계 — 변경 파악 및 task 분할 계획
- `git status`와 `git diff`(untracked는 내용 확인)로 전체 변경을 읽는다.
- 변경을 **논리적 task 단위**로 묶는다. 묶는 기준:
  - 같은 기능/화면/관심사(예: order 액션 칩 통일, hero 이미지 사이즈, package-plans 동기화)
  - `.claude/` 메타 파일(settings, commands, 스크린샷 등)은 별도 `chore` 커밋으로 분리
  - 함께 동작해야 의미가 있는 파일(예: 컴포넌트 + 그 컴포넌트가 import하는 신규 훅)은 같은 커밋
- 다음이 섞여 있으면 사용자에게 먼저 알리고 진행 여부를 확인한다(있어도 되지만 눈에 띄게 짚고 넘어간다):
  - `package.json`/lockfile, `next.config.*`, `tsconfig.json`, 미들웨어(`proxy.ts` 등), `.github/workflows/*`, `.env*`
  - `.env`, `*.pem`, `*key*`, `*secret*`, `*credential*` 등 이름만으로 민감정보가 의심되는 파일, 또는 diff 내용에 `AKIA`, `-----BEGIN`, `SECRET=`, `PASSWORD=` 같은 패턴
- 분할 계획(커밋 N개, 각 커밋의 파일·메시지 초안)을 **먼저 출력**한다.

### 2단계 — 정적 검증 (CLAUDE.md 작업 검증 규칙)
```
npx tsc --noEmit -p .
pnpm lint
```
- **신규** 오류만 수정 대상. 기존부터 있던 오류는 건드리지 않는다.
- 신규 타입/린트 오류가 있으면 고치고 다시 검증한다. 못 고치면 중단·보고.

### 3단계 — Playwright E2E 테스트
```
pnpm test
```
- webServer 설정이 `pnpm build && pnpm start`(PORT 3001)이라 최초 실행은 빌드 포함 최대 5분 소요된다. 이 단계가 빌드+부팅 확인을 겸한다.
- **`reuseExistingServer`가 켜져 있어(로컬 한정) 3001에 서버가 떠 있으면 빌드를 건너뛰고 재사용한다.** 방금 코드를 바꾼 상황에서 이러면 **오래된 빌드로 테스트가 통과해버리는 오탐**이 난다. 그래서 테스트 실행 전에 다음을 확인한다:
  1. 3001 포트가 비어 있으면 → 그대로 `pnpm test` 실행(빌드부터 새로 돈다).
  2. 3001이 점유돼 있으면 → `.next` 빌드 산출물의 수정 시각과 이번에 변경된 소스 파일들의 수정 시각을 비교한다. `.next`가 더 오래됐으면 그 서버는 **stale**이다.
  3. stale이거나 판단이 서지 않으면 → **직접 죽이지 말고 멈춘다.** 3001을 누가 점유 중인지(다른 세션이 테스트를 돌리는 중일 수 있다) 보고하고, 사용자에게 정리를 요청한 뒤 재개를 기다린다. (핵심 정책 5)
- 결과 판정:
  - **전부 통과** → 4단계로 진행
  - **하나라도 실패** → **여기서 중단.** 실패한 spec·테스트명·오류 요약을 보고하고 커밋하지 않는다. (핵심 정책 1)

### 4단계 — task별 커밋
- 1단계 계획대로 `git add <해당 파일들>` 후, `git diff --cached`로 실제로 커밋될 내용을 한 번 더 확인한다(의도치 않게 딸려온 파일이 없는지). 그 다음 `git commit`을 task마다 반복한다.
- 커밋 메시지는 이 저장소 컨벤션(한국어, `feat:`/`fix:`/`chore:` 프리픽스, 무엇을 왜 바꿨는지)을 따른다. 최근 `git log`로 톤을 맞추고, 끝에 Claude 저작자 표시(핵심 정책 6)를 붙인다.
- 현재 브랜치가 기본 브랜치(main)면 커밋하기 전에 먼저 확인받는다(핵심 정책 4).

### 5단계 — 결과 보고
- 만든 커밋 목록(`git log --oneline -N`)
- tsc / lint / playwright 결과 한 줄 요약
- 커밋하지 않고 남겨둔 변경이 있으면 그 이유

## 출력 형식

- 분할 계획 표 (커밋 # · 파일 · 메시지)
- 정적 검증 결과 (tsc / lint)
- Playwright 결과 (통과/실패, 실패 시 상세)
- 최종 커밋 로그
