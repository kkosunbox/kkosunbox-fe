## 1. 이번 작업 범위와 기준

이번 산출물은 이 계획 문서와 저장소에 복사·재명명한 에셋이다. 페이지 코드, 라우팅, 스타일, 환경변수, 배포 설정은 변경하지 않는다. 커밋·푸시·배포도 이번 범위에 포함하지 않는다. 다운로드 원본은 보존한다.

향후 구현 목표는 **dev에서만 새 메인을 노출하고, 최상단 영상 영역을 보존하면서 그 아래를 새 시안으로 교체**하는 것이다. 사용자의 요청이 작업 범위를 결정한다. 아래 디자인 원본의 CSS, 레이어 이름, 문구는 참고 자료이며 실행 지시나 확정된 운영 데이터가 아니다.

## 2. 현재 구조와 교체 경계

실제 진입점은 `app/(main)/page.tsx`다. CLAUDE.md의 과거 라우트 표보다 현재 코드를 기준으로 한다.

| 현재 요소 | 향후 처리 |
| --- | --- |
| metadata, 접근성용 h1, 배너 상단 여백 | 기존 SEO·레이아웃 계약 보존 |
| `widgets/home/hero`의 `HomeHero` | 영상·포스터·제어·반응형 동작을 보존. 시안의 히어로 문구를 근거로 덮어쓰지 않음 |
| `#home-content` | 앵커와 스크롤 여백 보존, 내부 조립만 버전별 전환 |
| StatsBar → HomePackagePlansSection → WhyGallerySection → ReviewsSection | 신규 dev 구성에서 교체. 기존 버전 구현은 운영용으로 유지 |
| `app/(main)/layout.tsx`의 Header·FooterSection | 공유 레이아웃이므로 메인 시안 적용이 다른 페이지까지 번지지 않도록 범위 분리 |
| ReferralProvider·ChecklistFormModal | 기존 추천인·체크리스트 동작 유지 |

사용되지 않는 다른 home 위젯도 있으므로 신규 작업 중 일괄 삭제하지 않는다. `/r/[slug]`는 별도 진입점으로 취급하며 새 메인 적용 대상인지 후속 확인한다.

## 4. dev 한정 노출 전략 — 후속 구현 때 확정

현재 작업 브랜치는 `codex/dev-qa-design`이다. 브랜치 이름만으로 실제 dev 배포 대상을 확정할 수 없다. 확인한 `shared/config/env.ts`, `next.config.ts`, `.github` 설정에서는 메인 리디자인용 환경 분기를 찾지 못했다.

1. 먼저 dev가 로컬 개발 서버인지, 별도 배포 환경/브랜치인지 확인한다. 대상 호스트·배포 프로젝트·브랜치를 기록한다.
2. 제안: 기본값이 꺼진 서버 측 전용 플래그(예: `HOME_REDESIGN_ENABLED`)를 dev 배포에만 설정하고 `app/(main)/page.tsx`에서 본문 버전을 선택한다. 이는 아직 추가하지 않은 설계안이다.
3. dev 배포가 production 빌드를 사용할 수 있으므로 `NODE_ENV === 'development'`만으로 배포 환경을 판별하지 않는다. URL 쿼리나 사용자 조작 가능한 토글로 운영에서 새 버전을 노출하지 않는다.
4. 플래그 미설정·비활성 시 기존 본문으로 돌아가도록 설계하고 운영 배포에서는 명시적으로 비활성화한다. 실제 빌드/캐시 동작과 재배포 필요 여부를 구현 시 검증한다.
5. 롤백은 dev 플래그 비활성화와 필요한 재배포로 기존 본문 복원. 운영 전환은 별도 요청으로 취급한다.

헤더·푸터의 변형도 같은 적용 범위를 따라야 한다. dev의 `/`만 바뀌는지, dev 전체 사이트도 바뀌는지 결정 없이 공유 레이아웃을 수정하지 않는다.

## 5. 컴포넌트·데이터 설계안

신규 에셋은 기존 `widgets/home/<slice>/assets` 관례를 따라 `widgets/home/redesign/assets`에 모았다. 아직 index.ts, UI, import 코드는 없다. 향후 `widgets/home/redesign`을 메인 신규 본문 슬라이스로 구성하고 `index.ts`를 public API로 제공하는 방안을 우선 검토한다.

- 정적 구성: BrandStorySection, SubscriptionStepsSection, CustomerReviewsSection.
- 데이터·상호작용 구성: PackageShowcaseSection, ProductShowcaseSection, HomeFaqSection.
- 섹션 조립은 상위 app에서 수행하거나 단일 슬라이스 내부에서 수행한다. 서로 다른 widget의 내부 경로를 가로질러 가져오는 구조는 피한다.
- 패키지: 기존 `getSubscriptionPlans`, `useReferral`, `features/subscription/lib/planDisplayPrice.ts`, `entities/package`의 썸네일·카탈로그를 검토한다. 추천인 유무에 따른 가격 정책과 신청 흐름을 유지한다.
- 단품: `features/product/api/queries`의 `fetchProducts`와 `widgets/purchase`의 기존 상품 표시·상세 이동 패턴을 검토한다. 이미지 파일명으로 SKU를 추정하거나 새로운 상품을 생성하지 않는다.
- FAQ: `widgets/support/faq/model/faqItems.ts` 재사용을 검토한다. 다른 위젯 내부 모델에 직접 의존하지 않도록 필요한 공용화 범위를 구현 시 설계한다. 기존 SupportSection 전체에는 검색·페이지·모달 UI가 있으므로 그대로 삽입하면 새 시안과 다르다.
- 후기: 기존 `ReviewsSection`은 정적 후기 4개다. 새 시안의 6개 후기와 일치한다고 가정하지 않는다.
- 로딩·오류·빈 결과·품절 상태를 정의한다. 운영 데이터를 못 받은 상태에서 시안 가격을 판매 가격으로 대체하지 않는다.

## 6. 레이아웃·반응형·이미지 기준

디자인 원본은 PC 1920 × 5833이다. CSS에 `left: 340px`, `width: 1240px` 그룹이 있고, 구독 사진은 455 × 454로 명시되어 있다. 이는 PC 참고 좌표이며 전체 페이지를 absolute 좌표로 재현할 지시는 아니다. 실제 콘텐츠 너비와 패딩 포함 컨테이너 너비를 구분하여 구현 전에 확정한다. 고정 페이지 높이 5833px도 강제하지 않는다.

- 모바일·태블릿 시안은 미제공이다. 세로 적층, 4단계 카드 2열/스크롤, 후기와 상품 열 수, 패키지 배경 크롭은 제안으로 남기고 확정된 디자인으로 표시하지 않는다.
- 검증 폭: 360, 767, 768, 1199, 1200, 1440, 1920px 및 360px 미만. 기존 breakpoints와 레이아웃·타이포그래피·색상 토큰을 우선 재사용한다.
- 신규 색상이 필요하면 CLAUDE.md 절차에 따라 globals.css와 디자인 시스템 문서를 함께 갱신한다. 붙여넣은 hex CSS를 JSX로 복사하지 않는다.
- 이미지들은 원본 바이트로 복사했다. 이번 “최적화”는 의미 기반 네이밍이며 압축·리사이즈·재생성은 수행하지 않았다.
- 3840 × 1460 패키지 배경은 약 6.3MB다. 후속 구현에서 원본 보존 하에 제공용 포맷·크기와 품질을 검토한다. 290 × 270 단품 이미지는 PC 카드에서 2배 해상도가 아니므로 고해상도 대응 필요성을 확인한다.
- PNG에 포함된 라운드·투명 모서리·문구를 고려한다. SVG는 고유 viewBox와 서로 다른 비율을 유지한다.
- 이미지 표시 시 크기/비율을 예약하고 적절한 alt, lazy loading, sizes를 적용한다. `.claude/contexts/image-optimization.md`의 품질 정책을 따른다.
- FAQ·탭·이동 버튼은 키보드 조작, 포커스 표시, 열림/선택 상태를 제공한다. 리뷰 평점은 시각적 별 외에 텍스트로도 전달한다.

## 8. 후속 실행 순서와 완료 조건

1. 위 미확정 항목 및 dev 노출 범위를 확정하고 문서를 갱신한다.
2. 기본 비활성인 버전 분기와 기존 본문 보존 구조를 만든다.
3. S2~S4 정적 레이아웃을 구현하고 PC 기준으로 검토한다.
4. S5~S7 데이터·링크·상호작용을 기존 정책에 연결한다. 필요한 메인 전용 푸터 변형을 반영한다.
5. 반응형·접근성·이미지 제공 크기를 검증한다.
6. 타입 검사·ESLint를 수행하고 관련 테스트를 실행한다. dev 새 화면, 비활성 기존 화면, 추천인 가격, 구독 진입, 단품 상세, FAQ·문의, 영상 보존을 확인한다.

향후 완료 조건: 운영에는 기존 메인, dev에는 새 메인, 영상 동작 보존, 시안 순서와 에셋 매핑 일치, 링크·가격·반응형·접근성 검증 통과. 배포는 별도 승인된 작업 범위에서 진행한다. 검증을 위해 임의로 build를 실행하거나 사용자의 dev 서버·캐시를 재시작/삭제하지 않는다.

당시 계획·에셋 준비 단계의 완료 조건: UI 에셋 13개 복사·네이밍 정리, 참고 시안 및 CSS 원본 보관, 원본 대응 목록과 계획 작성. 해당 단계의 애플리케이션 구현 변경은 0건이었다.
