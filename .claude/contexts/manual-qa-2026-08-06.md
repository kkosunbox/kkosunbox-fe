## 0. 상태 조합 시나리오 테스트 (가장 중요 — 먼저 읽을 것)

아래 A~I는 **커밋 단위/기능 단위** 체크리스트라 "그 화면 하나"는 검증되지만, 실제 유저는 여러 기능을 **겹쳐서** 만난다. 오늘 코드를 직접 읽고 찾아낸, 아직 아무 자동테스트도 커버하지 않는 "조합" 지점들이다. 각 시나리오는 **왜 위험한지 근거 코드 위치**를 같이 적었다.

### 시나리오 1 — 이미 구독 중인 유저가 단건구매 → 배너로 2차 구독

**재현**: 구독 1개 보유 상태로 로그인 → 단품 구매(`/purchase/order`) 완료 → `/mypage/purchase` 상세 → "잠깐! 구독하면 15% 더 저렴해요" 배너 → "구독하러 가기" → 구독 완료까지 진행.

**왜 위험한가**: `useOrderSectionState`가 이 진입을 "이미 구독 이력 있음(`hasSubscriptionHistory=true`) + 프로모 배너 진입(`showStartDateOption=true`)"으로 처리하는데, 이 두 조건이 **동시에 참인 경로는 오늘 처음 열렸다** — `features/order/lib/inviteSectionMode.ts`상 `hasSubscriptionHistory=true`면 초대코드 섹션은 무조건 `hidden`이라 "구독 시작일 섹션만 보이고 초대코드 섹션은 없는" 화면 배치는 기존에 없던 조합이다.

- [ ] 1-1. "구독 시작일" 섹션만 보이고 초대코드 섹션은 안 보이는지 (있으면 버그).
- [ ] 1-2. 2번째 구독 생성이 정상 완료되는지(기존 구독을 덮어쓰거나 충돌 에러가 나지 않는지).
- [ ] 1-3. 완료 후 `/mypage/subscription`에서 **기존 구독 + 신규 구독 + 단건구매 이력**이 `SubscriptionCard`의 캐러셀 슬라이드로 다 보이는지 (`widgets/mypage/ui/SubscriptionCard.tsx`가 `subscriptions[]`와 `purchaseGroups[]`를 합쳐 슬라이드 배열을 만드는 구조 — 슬라이드 3개 이상에서 인디케이터·전환이 안 깨지는지).
- [ ] 1-4. 두 구독의 다음 배송일이 서로 다르게(신규 구독은 "다음 배송부터 시작"에서 고른 날짜로) 정상 표시되는지 — 결제 주기가 겹치거나 뒤섞이지 않는지.
- [ ] 1-5. `/mypage/subscription/change`(구독 변경) 진입 시 **어느 구독을 바꾸는 건지** 명확히 구분되는지 — 다중 구독 지원이 아직 "구독 변경 페이지는 단일 구독 가정"이라는 미해결 과제로 남아있었음([[project_multi_subscription]] 메모리 참고). 지금 시점에 실제로 어떻게 동작하는지 반드시 확인.

### 시나리오 2 — 초대코드로 처음 들어온 유저가 단건구매부터 하고 나중에 배너로 구독

**재현**: 시크릿창 → `?ref=코드` 링크로 진입(구독 이력 없음, 즉 `hasSubscriptionHistory=false`) → 로그인/가입 → 단품 구매 먼저 진행 → `/mypage/purchase` 상세 → 배너로 `/order?...&from=purchase` 진입.

**왜 위험한가**: 이번엔 `hasSubscriptionHistory=false`라서 `getInviteSectionMode`가 `"locked"`(초대코드 자동 적용)를 반환 — **초대코드 섹션 + 구독 시작일 섹션이 동시에 열리는 조합**도 오늘 처음 가능해졌다. 게다가 `computeOrderPricing`(`features/order/lib/orderPricing.ts`)은 쿠폰 할인율과 초대코드 할인율을 **더해서** 적용하도록 설계돼 있다 — 의도된 정책인지 재확인 필요.

- [ ] 2-1. 초대코드 섹션(자동 적용, locked)과 구독 시작일 섹션이 레이아웃 안 깨지고 같이 보이는지.
- [ ] 2-2. 이 화면에서 쿠폰 코드도 추가로 입력해 적용 — 최종 금액이 "초대코드 할인 + 쿠폰 할인"이 **중첩 적용**되는지 직접 계산해서 확인. 중첩이 맞다면 통과, 의도치 않은 것 같으면 정책 담당자에게 확인 필요한 항목으로 별도 기록.
- [ ] 2-3. 구독 완료 후 초대코드 배지/쿠키가 정상 소비(`markInviteConsumed`)되고, 이후 재방문 시 되살아나지 않는지([[project_referral_badge_purchase_fix]]에서 이미 한 번 레이스로 터졌던 지점 — 새 진입경로라 재발 여부 확인 가치 있음).

### 시나리오 3 — 단건구매 쿠폰 vs 구독주문 쿠폰, 같은 코드 넣어보기

**재현**: 단품 구매(`/purchase/order`)에서 쿠폰 코드 `ABC123`을 적용 → 결제는 하지 말고 이탈 → 구독 주문(`/order?planId=...`)의 쿠폰 입력란에 똑같이 `ABC123` 입력.

**왜 위험한가**: `usePurchaseCoupon.ts` 주석에 명시돼 있듯 이 둘은 **완전히 다른 백엔드 엔드포인트**(`getProductCouponInfo` vs 구독 쪽 별도 검증)를 쓰는 별개 쿠폰 체계다. UI 입력창은 똑같이 생겼는데 뒤에서 다른 쿠폰 풀을 조회하므로, 유저 입장에선 "왜 아까는 됐는데 여기선 안 되지"로 보일 수 있다.

- [ ] 3-2. 반대 방향(구독용 쿠폰을 단건구매 쿠폰란에)도 동일하게 확인.
- [ ] 3-3. 두 쿠폰 입력 UI가 시각적으로 완전히 동일해서 유저가 "같은 기능"이라고 착각할 소지가 있는지 — 필요하면 안내 문구(예: "구독 전용 쿠폰입니다") 추가가 나을지 판단.

### 시나리오 4 — 배너 경유 vs 직접 진입, 같은 플랜을 서로 다른 경로로 재구독

- [ ] 5-2. 초대코드 첫달할인 배지가 뜨는 화면과 이 배너가 같이 보일 때, 두 수치가 사용자에게 명확히 구분되는지.
