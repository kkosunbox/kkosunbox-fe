단건은 같은 날 주문 총액 기준으로 바뀌었지만 **구독은 안 바뀌었음이 실데이터로 확인**됐다.

**⚠️ 서버 응답이 스펙과 다른 지점 — `discountType`으로만 분기해야 한다**

`spring30`은 `discountType: "fixed"`인데 **`discountRate: 30`도 함께 내려온다.** 스펙에는
"정액 할인일 때만 `discountAmount`에 값이 있음"이라고 돼 있지만 실제 응답은 두 필드가 다 차 있다.
어느 필드가 채워졌는지로 타입을 추론했다면 **10,000원이 아니라 5,370원(17,900 × 30%)으로 계산**됐을 것.
현재 구현은 `discountType`으로 분기하므로 정상 — 기간 연장된 실제 쿠폰으로 확인한 결과
`봄맞이 특별 할인 -10,000원` / 총 주문금액 7,900원으로 정확히 계산된다. 단위 테스트로도 고정해 뒀다.

**구독의 "단가 1개 기준"이 서버 청구로도 확인됨** — 프리미엄 6BOX 구독(#76)에 10% 쿠폰:
173,400원(28,900 × 6) 중 **2,890원(= 28,900 × 10%)만 할인**돼 170,510원이 청구됐다.
수량 6개인데 단가 1개분만 할인 → 구독 규칙 유지가 맞다는 실결제 증거.

## 0. 상태 조합 시나리오

### 시나리오 0-1 — 정액(fixed) 쿠폰으로 **구독** 결제 🔴

**재현**: 백엔드에서 `discountType: "fixed"` 쿠폰 발급 → `/order?planId=1` → 쿠폰 적용 → **총 주문금액을 적어두고** → 구독하기 → `/mypage/subscription/detail` 결제 이력 금액과 비교.

**왜 위험한가**: 구독은 단건과 달리 **결제 직전 서버 금액으로 재동기화하는 단계가 없다**. `createSubscription` 호출이 곧바로 빌링키 청구로 이어지므로, 프론트 계산이 어긋나면 **사용자가 확인할 기회 없이 다른 금액이 청구된다**. 정액 할인을 수량 2개 이상에서 서버가 1회만 빼는지 스펙에 없어, 프론트는 "1회 적용"으로 구현해 둔 상태다.

- [x] 0-1-3. 정액 쿠폰 라벨이 **금액**으로 표시 ✅ (`봄맞이 특별 할인 -10,000원`)
- [x] 프론트 계산이 단가 1개 기준을 유지 ✅ (수량 3개 실측)
- [x] 정률 쿠폰은 서버 청구까지 일치 확인 ✅ (구독 #76, 위 표 참조)
- [ ] 0-1-1. **정액 쿠폰**(`spring30`)으로 실결제 → 주문서 총 주문금액 = 결제 이력 금액
- [ ] 0-1-2. 정액 쿠폰 + **수량 2개 이상** — 정액이 1회만 차감되는지
- [ ] 0-1-4. `applyCount ≥ 2` 쿠폰이면 다음 갱신 결제에도 할인이 유지되는지 (dev에 해당 쿠폰 없음 — 갱신일 이후 재확인)

### 시나리오 0-2 — 단건 쿠폰 할인 기준 변경 확인 🔴 **(코드 수정 완료 — 실결제 검증만 남음)**

**확정된 정책 (2026-08-11, 백엔드 협의 완료)**
- 단건 쿠폰: **할인율은 주문 총액에, 상한은 주문 전체에 1회.** "1개 상품 할인 lock"은 폐지.
- 상한 없는 쿠폰과 있는 쿠폰을 분리 운영(`maxDiscountAmount`가 `null`이면 무제한).
- **구독 쿠폰·초대코드는 단가 1개 기준 유지** — 단건을 따라 바꾸지 않는다.

프론트는 이 규칙대로 구현·검증 완료. 추가 코드 변경 없음.

부수 효과로 **상한(`maxDiscountAmount`)이 이제 실제로 작동한다** — 이전 기준(단가 1개)에서는 `summer20`·`vip30` 모두 상한에 영원히 도달할 수 없어 기능이 죽어 있었다.

**수정 후 실측** (`/purchase/order?tier=Premium&quantity=3`, 주문상품금액 101,700원):

| 코드 | 계산 | 화면 표시 | 총액 |
|---|---|---|---|
| `welcome10` | 101,700 × 10% (상한 없음) | -10,170원 | 91,530원 |
| `summer20` | 101,700 × 20% = 20,340 → **상한 10,000 적용** | -10,000원 | 91,700원 |
| `vip30` | 101,700 × 30% = 30,510 (상한 50,000 미달) | -30,510원 | 71,190원 |

**실결제로 검증 완료 (2026-08-11)** — 스탠다드 BOX × 5개, `welcome10`:

```
주문상품금액        134,500원   (26,900 × 5, 카탈로그 단가와 일치)
총 쿠폰 할인금액     -13,450원   = 134,500 × 10%  ← 주문 총액 기준 확정
배송비                  -0원
총 결제금액         121,050원   = 134,500 − 13,450 ✓
```

완료 화면의 할인액은 프론트 계산이 아니라 **`주문상품금액 − 서버 결제금액` 역산**이다. 즉 13,450원은
**서버가 실제로 깎아준 금액**이고, 그게 정확히 주문 총액의 10%다 → **서버 기준이 주문 총액임이 실결제로 증명**.
(예전 로직이었다면 주문서에 2,690원으로 표시되고 실제로는 13,450원이 깎여 **10,760원 차이**가 났을 것.)

- [x] 0-2-1. 주문서 표시 할인 = 실제 청구액 ✅
- [x] 0-2-2. 완료 화면 할인액 = 서버 값 ✅
- [ ] 0-2-3. 상한이 걸리는 조합 실결제 — 규칙은 백엔드 확답으로 확정됐고 프론트도 그대로
      구현했으므로 **위험은 낮다(🟡)**. 확인하려면 `summer20` + 스탠다드 5개
      (134,500 × 20% = 26,900 → 상한 10,000원 표시)로 1건 결제해 청구액을 대조하면 된다.

### 시나리오 0-3 — 카드 등록 직후 **연속으로** 다시 변경 🟡

**재현**: 카드 미등록 계정 → `/mypage` → 결제등록/변경 → 등록 완료 → **모달 확인만 누르고 새로고침 없이** 곧바로 다시 결제등록/변경 → 다른 카드로 변경.

**왜 위험한가**: 등록/변경 문구는 **서버 prop**(`initialBillingInfo`) 기준으로 판정한다. 첫 등록 후 `router.refresh()`가 끝나야 prop이 "카드 있음"으로 바뀌므로, 그 전에 두 번째를 마치면 **두 번째에도 "등록"이 뜰 수 있다**. (단발 등록·변경은 각각 실측 통과 — 연속 케이스만 미확인)

- [ ] 0-3-1. 두 번째에 "결제수단이 **변경**되었습니다."가 뜨는지 ("등록"이면 타이밍 버그)
- [ ] 0-3-2. `/mypage`와 `/mypage/subscription`을 **두 탭에 동시에** 띄운 상태로 카드 등록 → 두 탭 모두 모달이 뜨는지 (BroadcastChannel 특성상 정상 — 거슬리는 수준인지 판단만)

### 시나리오 0-5 — 구독 목록·대시보드 "결제금액" 할인 반영 🔴 **(코드 반영 완료 — 실화면 검증만 남음)**

**해결된 증상**: 같은 구독(#76)이 목록 173,400원 / 상세 170,510원으로 어긋나던 문제.

**받은 필드 (2026-08-12, 백엔드)** — `GET /v1/subscriptions` → `UserSubscriptionDto.lastPaidAmount`

> 쿠폰·레퍼럴 할인이 전부 반영된, `subscription_payment` 테이블의 가장 최근 Completed 결제의
> `amount`(부가세 포함 최종 금액). 결제가 한 번도 완료된 적 없는 구독(예약 구독 포함)은 `null`.

### 반영 내용

| 위치 | 변경 전 | 변경 후 |
|---|---|---|
| `/mypage/subscription` 목록 카드 (`SubscriptionManagementSection.tsx:340`) | `결제금액 : 173,400원` (정가×수량) | `결제금액 : 170,510원` (`lastPaidAmount`) |
| `/mypage` 대시보드 카드 (`SubscriptionCard.tsx:323`) | `결제금액 : 173,400원` (정가×수량) | `결제금액 : 170,510원` (`lastPaidAmount`) |
| 목록 상단 요약 (`SubscriptionManagementSection.tsx:164`) | **`예상 결제 금액`** : 정가 합계 | **`결제 금액`** : `lastPaidAmount` 합계 |

값 접근은 전부 `features/subscription/lib/subscriptionAmount.ts`를 거친다
(`subscriptionPaidAmount` / `totalSubscriptionPaidAmount`). 서버가 나중에 "다음 결제 예정액"을
내려주면 이 파일의 참조 필드만 바꾸면 된다.

### 라벨에서 "예상"을 뺀 이유 (중요)

`lastPaidAmount`는 **과거값**이다. 그런데 이 프로덕트의 할인 두 종류가 **둘 다 회차 제한형**이라
"구독은 한번 정해진 금액이 계속 나간다"는 전제가 성립하지 않는다.

| 할인 | 지속성 | 근거 |
|---|---|---|
| 레퍼럴 | **첫 달만** | `ReferralAdditionalDiscountChip.tsx:27` — 배지 문구가 `첫 달 {pct}%추가할인` |
| 쿠폰 | `applyCount` 회차만 | `features/subscription/api/types.ts` — dev `welcome10`은 `applyCount: 1` |

즉 **할인이 없는 구독은 `lastPaidAmount == 정가×수량`이라 이 필드가 필요 없고, 필요해지는 순간
(할인이 걸린 구독)은 대부분 다음 달에 값이 바뀐다.** #76이 정확히 그 케이스 — 첫 결제 170,510원,
다음 결제(9/11)는 할인 소진으로 173,400원. 여기에 "예상 결제 금액 : 170,510원"이라 쓰면
실청구보다 2,890원 낮게 안내하게 된다. 그래서 상단 라벨에서 "예상"을 제거했다.

프론트가 다음 결제액을 유도할 방법은 없다 — `GET /v1/subscriptions`에 쿠폰 정보가 없고
결제 이력에도 잔여 회차가 없다. 필요해지면 백엔드에 `nextBillingAmount`를 별도로 요청해야 한다.

### `null`(결제 이력 없음) 처리

정가로 대체하지 않고 `-`로 표시한다. 예약 구독은 아직 결제가 일어나지 않았으므로 정가를 넣으면
확정 금액처럼 보이는 같은 종류의 거짓말이 된다. 상단 합계는 `null`인 구독을 합산에서 제외하고,
합산할 값이 하나도 없으면 `-`.
