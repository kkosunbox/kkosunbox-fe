## ⏸ 실측 중 발견 — 포인트 **월 이동이 400으로 실패**한다 (홀딩)

이번 6커밋과 **무관한 기존 결함**이지만, 포인트 화면을 실제로 밟다가 확인됐다.

> **2026-08-12 보류 결정**: 실제 인플루언서가 없어 지금은 영향받는 사용자가 0명이다.
> 인플루언서 기능이 실제로 열릴 때 이 섹션부터 다시 볼 것. **증상·원인은 아래에 확정돼 있으니 재조사 불필요.**

**재현**: 인플루언서 계정 `/mypage/point` → 상단 월 네비게이션의 `‹`(이전 달) 클릭.

**결과**: **"요청 정보를 확인해주세요."** 알림 모달이 뜨고 월이 바뀌지 않는다. 네트워크 실측:

```
GET /v1/points/balance?year=2026&month=7   → 200   ← 잔액은 정상
GET /v1/points?limit=200&year=2026&month=7 → 400   ← 내역 API가 year/month를 거부
```

즉 **잔액 엔드포인트는 `year`/`month`를 받는데 내역 엔드포인트는 거부한다.**
`usePointMonthQuery.loadMonthData`가 두 요청을 `Promise.all`로 함께 보내므로 월 이동이 항상 실패한다.

**초기 진입과의 관계 — 확정 못 한 부분**: SSR 초기 호출은 `fetchPointHistory(token, { limit: 200 })`로
**`year`/`month` 없이** 부른다. 이게 200인데 진짜로 빈 배열인지, 아니면 이것도 실패해
`.catch(() => ({ items: [] }))`에 삼켜진 건지는 **브라우저에서 판별 불가**다
(잔액 10,557P는 정상이므로 토큰·백엔드 자체는 살아 있다).
→ 시나리오 0-2가 경고한 "실패가 정상 빈 상태로 보인다"가 실제로 발생한 사례.

- [ ] **N-1.** 백엔드에 `GET /v1/points`의 `year`/`month` 파라미터 지원 여부 확인 — 지원 안 하면 프론트가 안 보내야 하고, 지원해야 하면 400 원인 확인
- [ ] **N-2.** `누적 10,557P`인데 내역이 0건인 것이 실제 데이터인지 확인 (잔액만 있고 원장이 없는 상태가 정상인가)
- [ ] **N-3.** 위가 정리되면 `fetchPointHistory`의 `.catch()` 무음 처리를 유지할지 결정 — 유지하면 장애를 영원히 못 본다
