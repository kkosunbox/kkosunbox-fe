## 0. 가장 먼저 실행할 상태 조합

### S01 — 주문은 있는데 조회 API 일부만 실패 🔴

준비: 구독·단품 주문이 각각 있는 테스트 계정. 정상 응답 기준 주문번호와 건수 기록.
재현: 마이페이지 → 주문내역 → 상세 순서로 정상 조회 후, 개발 환경에서 목록·유형별 건수·상세 API를 **하나씩** 500 또는 시간 초과로 바꾸어 다시 진입. 복구 후 새로고침.
왜 위험한가: `features/payment/api/queries.ts`의 `fetchCombinedPaymentHistory`는 실패를 빈 목록, `fetchCombinedPaymentTypeSummary`는 0건, `fetchCombinedPayment`는 null로 바꾼다. `app/(main)/orders/[orderType]/[id]/page.tsx`는 null을 404로 처리한다. 코드상 위험이며 이번에 실제 장애를 재현한 결과는 아니다.

- [ ] S01-1 목록 실패를 실제 주문 0건처럼 안내하지 않는다. 기존 주문이 사라졌다고 오해하게 만들면 실패 후보로 기록한다.
- [ ] S01-2 목록 성공·건수 실패 및 그 반대에서 카드 수와 탭 수가 불일치하는지 각각 확인한다.
- [ ] S01-3 유효한 주문 상세의 일시 장애와 존재하지 않는 주문을 구분하거나 재시도 가능한 안내를 제공한다.
- [ ] S01-4 복구 후 원래 주문·건수가 다시 나오고 빈 상태가 계속 남지 않는다. 원시 영문 서버 오류를 노출하지 않는다.

### S02 — 쿠폰 적용 직후 해제 + 응답 순서 역전 🔴

준비: 선택 상품이 있는 장바구니, 유효한 쿠폰 A/B. 개발용 API 응답 지연을 제어할 수 있어야 한다.
재현: 장바구니 주문서에서 A 적용 요청을 늦춘 상태로 쿠폰 사용 해제 → 해제 요청을 먼저 완료 → A 요청을 뒤늦게 완료. 이어 A→B 연속 적용도 역순으로 응답시킨다.
왜 위험한가: `widgets/purchase/ui/CartOrderSection.tsx`의 `applyCoupon`, `toggleCoupon`이 각각 응답을 `setQuote`에 반영한다. 결제는 `checkoutCart` 결과로 위젯 금액을 다시 갱신하므로 화면 견적과 최종 금액을 함께 확인해야 한다.

- [ ] S02-1 마지막 사용자 선택이 해제라면 할인 금액이 다시 살아나지 않는다. A→B라면 B의 결과가 유지된다.
- [ ] S02-2 상단 요약·하단 합계·쿠폰 상태·Toss 결제창 금액·서버 주문 금액이 동일하다.
- [ ] S02-3 재계산 중 결제를 누르면 확정되지 않은 금액으로 진행하지 않는다. 변경된 금액은 결제 전에 알 수 있다.
- [ ] S02-4 쿠폰 만료/적용 실패 후 이전 할인만 남거나 정상 금액으로 돌아갈 수 없는 상태가 되지 않는다.

### S03 — 부분 환불 + 남은 수량 + 출고 상태 변경 🔴

준비: 개발 전용 주문. 두 상품 중 일부 수량을 환불한 주문, 출고 전/출고 후 주문을 각각 준비.
재현: 주문 상세에서 부분 환불 수량 확인 → 주문취소 확인창에서 돌아가기 → 다시 열어 취소 확정. 별도 주문으로 두 탭에서 같은 주문을 열고 한 탭에서 취소/출고 상태 변경 후 다른 탭에서 취소.
왜 위험한가: `OrderDetailSection.tsx:canCancel`은 단품·`PendingDelivery`·결제 완료/부분 환불·미환불 수량 존재를 조합한다. 확인창은 남은 상품 전체 취소를 안내한다. 화면 진입 후 서버 상태가 바뀔 수 있다.

- [ ] S03-1 돌아가기를 누르면 취소 요청이 없다. 확정 시 미환불 잔여 수량만 취소되며 이미 환불한 금액은 다시 환불되지 않는다.
- [ ] S03-2 전액 환불·출고 후·구독 주문에서 동일한 단품 취소 동작으로 진입하지 않는다.
- [ ] S03-3 두 탭·연속 클릭에도 취소 효과가 한 번만 발생한다. 서버 거절 시 성공 메시지를 띄우지 않는다.
- [ ] S03-4 상세·목록·마이페이지·영수증의 상태/금액이 갱신된다. 반영 지연이 있다면 운영 기준에 맞는 안내가 있다.

### S04 — 결제 결과는 서버에 반영됐지만 브라우저는 응답을 못 받음 🔴

준비: 테스트 결제키와 개발 주문. 결제 서버 담당자가 승인/주문 결과를 조회할 수 있어야 한다.
재현: 정상 테스트 결제 후 결과 반환을 지연/중단 → 사용자가 새로고침·뒤로가기·완료 URL 재방문. 주문취소도 별도의 개발 주문에서 서버 처리 후 응답 유실을 재현.
왜 위험한가: 결제 요청과 화면 이동, 주문취소와 `router.refresh()`는 별도 단계다. 브라우저 오류가 곧 서버 처리 실패는 아니다.

- [ ] S04-1 같은 결제/취소가 중복 처리되지 않는다. 서버 주문번호·거래번호·금액으로 한 건인지 대조한다.
- [ ] S04-2 확정되지 않은 결과를 성공/실패로 단정하지 않고 주문내역 조회 등 결과 확인 경로를 제공한다.
- [ ] S04-3 완료 URL 직접 접근·필수 쿼리 누락·금액 불일치로 성공 화면이나 임의 주문을 만들지 않는다.

### S05 — 기존 추천인 사용자 + 새 메인 + 빠른 이동 🔴

준비: 추천인 없음, 유효 추천인 A/B, 만료/비활성 코드. 할인 결과의 승인된 기준값 필요.
재현: A 랜딩 → 메인 → 구독 상세 → 뒤로가기 → B 랜딩 → 다시 메인/주문. 느린 응답에서도 반복.
왜 위험한가: `HomeRedesign.tsx`가 `useReferral().refCode`로 플랜을 재조회하고 `planDisplayPrice`로 표시한다. 과거 `referral-slug-switch-race-2026-09-07.md`에 전환 경합이 기록되어 있다. 오래된 문서의 미해결 표시는 현재 결함 확정이 아니며 회귀 확인 근거다.

- [ ] S05-1 추천인 표시·선택 플랜·가격이 현재 유효한 조건과 일치한다. 늦게 도착한 A 가격이 B를 덮지 않는다.
- [ ] S05-2 상세/주문까지 같은 가격 조건이 이어지고 일반 사용자에게 이전 추천인 정보가 섞이지 않는다.
- [ ] S05-3 비활성 코드에서 기존 코드 보존/해제 동작은 승인된 정책과 대조한다. 정책이 없으면 보류한다.

### S06 — 주문서 진입 뒤 상품 품절/삭제/가격 변경 🔴

준비: 일반 단품·패키지·여러 상품 장바구니. 개발 데이터에서 판매 상태를 바꿀 수 있어야 한다.

- [ ] S06-2 변경 가격이 결제 전에 명확히 표시된다. 오래된 카드 금액으로 결제하거나 예고 없이 더 큰 금액을 청구하지 않는다.
- [ ] S06-3 일부 상품 오류로 실패할 때 선택 상품/수량을 보존하거나 변경 내용을 명확히 알린다.

화면에서 빈 값만 바꾸는 것으로 서버 실패를 재현했다고 보지 않는다. 클라이언트 API는 개발용 네트워크 스텁/프록시를 사용하고, **서버에서 호출하는 주문내역 API는 테스트 백엔드 또는 서버 측 스텁으로 제어**한다. 브라우저 요청 차단만으로 서버 API가 실패했다고 가정하지 않는다. 실패 주입 응답·지연 순서·서버 결과를 증빙에 남긴다.

### 기록 규칙

각 체크박스/아래 표의 ID마다 `미실행 / 통과 / 실패 / 차단 / 정책확인 / 해당없음`을 기록한다. 준비 데이터나 권한이 없어 못 한 것은 차단이며 통과가 아니다. 해당없음에는 사유를 적는다.

```text
ID / 실행자 / 실행시각(KST):
환경 URL / 배포 커밋 또는 배포 ID / 시안 버전:
브라우저·버전 / OS / 실기기 여부 / CSS 너비×높이 / DPR / 확대율:
계정·데이터 ID(개인정보 제외) / 사전 상태:
재현 순서 / 기대 결과 / 실제 결과:
판정 / 이슈 링크 / 스크린샷·영상·요청 상태·서버 주문번호:
수정 커밋 / 재검증 환경·시각 / 재검증 판정:
```

카드 결제정보·토큰·실제 고객 주소/연락처는 증빙에 남기지 않는다. 스크린샷은 `환경_배포ID_시나리오ID_상태_너비x높이`로 이름을 붙인다.

## 5. 정책 확인 항목 — 디자인 수정으로 숨기지 않을 차이

1. 최신 FAQ는 일반 주문 **5만원 이상 무료배송**, 구독 전부 무료배송을 안내한다. 과거 QA는 단품 전액 무료배송 변경을 기록했다. 과거 문서를 현재 정책으로 사용하지 말고 단품·장바구니 견적과 최신 승인 정책을 대조한다. 쿠폰 적용 전/후 기준도 확인한다.
2. FAQ의 취소 가능 시점은 발송 전이다. 현재 `canCancel`의 `PendingDelivery`가 실제 출고 운영 상태와 같은 의미인지 확인한다. 부분 환불 후 남은 상품 전체 취소 범위도 확인한다.
3. 결제일 오전 8시, 월~목 오전 10시 이전 당일 출고, 제주/도서산간 제한은 **문구가 보이는 것**과 **실제 서비스가 그렇게 처리되는 것**을 분리한다. 운영/백엔드 검증 담당자를 지정한다.
4. 추천인·쿠폰 중복, 무료배송 판정, 주문 취소 시 쿠폰 복구는 승인 정책과 서버 기준값이 필요하다. 정책 없는 값은 테스트 작성자가 임의 확정하지 않는다.

## 6. 실행 순서와 종료 기준

### 권장 실행 순서

1. 배포·시안·지난주 업무 목록을 연결(D01~D04). 테스트 계정/주문/쿠폰 준비 여부를 기록한다.
2. 🔴 S01~S06 및 관련 B/C 시나리오를 개발에서 먼저 검증한다. 실패 시 담당자/재현 데이터를 확보한다.
3. 정상 데이터·예외 데이터 대표 화면과 R01~R07을 검사한다. 경계는 해당 화면 위주로 추가한다.
4. A·E 및 정상 B/C 흐름을 마무리하고, 수정 후 같은 실패 상태와 인접 정상 상태를 재검증한다.
5. 대상 릴리스 배포 후 라이브 비파괴 확인과 S08을 반복한다. 개발 통과를 라이브 통과로 복사하지 않는다.
