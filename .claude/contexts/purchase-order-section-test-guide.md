## 0. 시작 전 준비물

- [ ] `pnpm dev` → http://localhost:3000
- [ ] DevTools 열어둘 것 (Network 탭 + Console 탭)
- [ ] 접속 URL: **`http://localhost:3000/purchase/order?tier=Premium&quantity=2`**
  (`tier`는 반드시 `Premium` — 현재 단품 판매 중인 유일한 티어. 다른 값이면 `/purchase`로 리다이렉트된다)
- [ ] 로그인 불필요 — 비로그인 방문자도 구매 가능한 페이지다. 단, 로그인 상태면 마이페이지에 저장된 배송지로 P6을 테스트할 수 있어 더 편하다.
- [ ] 결제창 뜨는지 여부로 **백엔드 상품 카탈로그(`productId`) 매칭 상태**를 미리 확인해 둘 것:
  - 화면 하단 "결제하기"까지 눌러봤을 때 `productId === null` 안내("현재 이 상품은 준비 중입니다…")가 뜨면 → **P5는 이 상태 그대로 테스트**하고, P6~P12(실제 주문 생성)는 카탈로그에 상품이 매칭된 뒤에 진행할 것
- [ ] 테스트 카드 번호는 문서에 박아두지 않는다 — Toss 개발자센터 > 문서 > 테스트 카드 목록을 그때그때 참고
- [ ] 브라우저 콘솔에서 `[product-debug]`로 시작하는 로그를 확인할 것 — `POST /v1/products/{id}/orders`의 요청/응답이 **클라이언트 콘솔에 직접 찍힌다** (billing 쪽과 달리 서버 로그가 아니라 브라우저 F12로 바로 보임)

## 1. 착수 전 픽셀 베이스라인 (Phase 1 시작 **전에 딱 한 번**)

`/purchase/order`는 E2E도 픽셀 스냅샷도 0건이라 자동 안전망이 없다. Phase 5(View 분리) 완료 후 비교할 기준 스크린샷을 지금 찍어둔다.

1. 브라우저 창 폭을 아래 4단계로 바꿔가며 위 URL 전체 페이지를 스크린샷 (스크래치패드에 저장, 커밋 금지):
   - 초소형 359px / 모바일 390px / 태블릿 768px / 데스크탑 1280px
2. 각 폭에서 **"제품 정보"·"결제 수단"·"결제정보"·약관 패널을 한 번씩 접은 상태**도 1장씩 추가로 찍어둘 것 (Chevron·SectionCard 토글 클릭)
3. Phase 5가 끝나면 같은 URL·같은 폭으로 다시 찍어서 육안 1:1 대조

## 2. Phase 3 Exit Gate — 결제위젯 로드 검증 (W1~W6)

| # | 순서 | 확인할 것 |
|---|---|---|
| W1 | 페이지 새로고침 직후 "결제 수단" 카드 관찰 | "결제 UI를 불러오는 중…" 문구가 잠깐 보였다가, Toss 결제수단 선택 UI(카드/계좌이체 등 탭)로 바뀐다 |
| W2 | **DevTools → Elements 탭에서 `#purchase-payment-widget` 엘리먼트를 찾아 자식 `<iframe>` 개수 세기** | **정확히 1개**여야 한다. 2개 이상이면 결제위젯 effect의 deps가 오염된 것 — 리팩토링 코드에서 `total`을 deps에 넣지 않았는지 바로 확인 |
| W3 | "제품 정보" 카드에서 수량 +/− 버튼을 5번 이상 연타 | 결제 UI 안의 표시 금액이 수량을 따라 바뀌고, **W2에서 센 iframe 개수가 그대로 1개** (다시 Elements 탭에서 확인) |
| W4 | DevTools → Network 탭에서 요청 차단(Offline 체크) 후 페이지 새로고침 | "결제 UI를 불러오지 못했습니다. 잠시 후 다시 시도해주세요." 문구 + **"다시 시도" 버튼** 표시 |
| W5 | Network 탭 Offline 해제 → "다시 시도" 클릭 | 에러 문구가 사라지고 정상적으로 결제 UI가 로드된다 (W1과 동일 결과) |
| W6 | 페이지 진입 직후 곧바로 뒤로가기/다른 페이지 이동 (위젯 로드가 끝나기 전에) | Console 탭에 React의 "state update on unmounted component" 류 경고가 **찍히지 않는다** |

## 3. Phase 4·5 Exit Gate — 결제 오케스트레이션 회귀 (P1~P12)

**가드/검증 단계(P1~P5)는 카탈로그 매칭 여부와 무관하게 테스트 가능.** 실제 결제까지 가는 P6 이후는 상품이 매칭된 상태(§0)에서 진행.

### 3-1. 입력 검증 가드 (P1~P5) — 매번 페이지 새로고침 후 하나씩 확인

| # | 조작 | 기대 결과 |
|---|---|---|
| P1 | 아무 것도 입력하지 않고 곧바로 "결제하기" 클릭 | `"필수 약관에 동의해 주세요."` 가 결제 버튼 위에 빨간 글씨(인라인)로 뜬다. **Network 탭에 새 요청 0건** |
| P2 | "모두 동의합니다" 체크 → 배송지는 빈 채로 "결제하기" | `"배송지 정보(받는분, 연락처, 우편번호, 주소)를 입력해 주세요."` |
| P3 | 약관 동의 + 배송지 다 채우되 **전화번호를 `010-1`처럼 형식 틀리게** 입력 후 "결제하기" | 결제 버튼 위 문구가 아니라 **배송지 입력 필드 자체에** `"올바른 전화번호 형식이 아닙니다."` 에러가 뜬다 (인라인 필드 귀속 — submitError 자리와 다른 곳에 뜨는지 반드시 구분해서 확인) |
| P4 | §0에서 확인한 위젯 로드 실패 상태(Network Offline)에서 나머지 다 채우고 "결제하기" | `"결제 UI를 불러오는 중입니다. 잠시 후 다시 시도해주세요."` |
| P5 | 카탈로그에 상품이 매칭 안 된 상태(§0에서 확인됨)에서 모든 조건 충족 후 "결제하기" | `"현재 이 상품은 준비 중입니다. 잠시 후 다시 시도해주세요."` |

### 3-2. 실제 주문·결제 (P6~P12) — 상품이 카탈로그에 매칭된 상태에서만

| # | 조작 | 기대 결과 |
|---|---|---|
| P6 | (로그인 상태 + 저장된 배송지 있음) 저장된 배송지를 **선택**하고 결제하기 | Network 탭에 **배송지 생성 API 호출이 없어야 함** → 콘솔에 `[product-debug] → POST /v1/products/{id}/orders` 1건만 찍히고 → Toss 결제창이 뜬다 |
| P7 | **새 배송지를 직접 입력**해서 결제하기 | 배송지 생성 API 호출 → 그 다음 `[product-debug]` 주문 생성 호출, **이 순서로** 2건 발생 후 결제창 |
| P8 | 수량을 3으로 바꾼 뒤 결제하기 | 콘솔 `[product-debug]` 요청 페이로드에 `"quantity":3` 확인, 결제창에 뜨는 금액이 화면의 "단품구매" 총액과 일치 |
| P9 | Toss 결제창이 뜨면 **결제 진행하지 않고 취소(닫기)** | 에러 문구가 뜨지 않고, 버튼이 다시 "결제하기"로 돌아온다(로딩 상태 해제) |
| P10 | **테스트 카드로 실제 결제 완주** ⚠️ 이 시나리오가 가장 중요 | `/purchase/order/success`로 이동. **절대 `PRODUCT_ORDER_AMOUNT_MISMATCH` 에러가 나면 안 된다** — 이게 나면 `updateAmount(order.amount)` 앞의 `await`가 리팩토링 중 유실된 것이니 바로 코드 확인 |
| P11 | 테스트 카드로 **의도적으로 결제 실패**를 유도(한도초과 등 Toss 테스트 카드 활용) | `/purchase/order/fail`로 이동 |
| P12 | 결제 버튼 클릭 직후(요청 진행 중) 화면 관찰 | 버튼 문구가 `"결제 요청 중…"`으로 바뀌고 비활성화(disabled) 상태 — 연타해도 요청이 중복으로 나가지 않는다 |

> **P10을 건너뛰지 말 것.** 다른 검증은 다 통과해도 `await`가 빠진 회귀는 실제 결제를 끝까지 완주해야만 드러난다. 대부분의 경우 "우연히" 성공하다가 특정 타이밍에만 금액 불일치가 난다.

## 5. 문제 생겼을 때 볼 파일

| 증상 | 파일 |
|---|---|
| iframe 중복 생성 (W2·W3) | `usePurchasePaymentWidget.ts`의 effect deps — `[paymentWidget]` 유지했는지 |
| 금액 불일치(P10) | `handlePay` 안 `await updateAmount(order.amount)` — `await` 유실 여부 |
| 전화번호 에러가 엉뚱한 곳에 뜸(P3) | `validatePurchaseCheckout`의 sink 분기(`submitError` vs `phoneError`) |
| 배송지 생성이 중복 호출됨(P6) | `address.selectedAddressId ?? (await address.createAddress())` — `??` 단축평가 유실 여부 |
| 취소 시 에러 문구가 뜸(P9) | `isTossUserCancel(err)` 분기 — catch 블록에서 조용히 return 하는지 |
| 결제 버튼이 중복 클릭됨(P12) | `isPaying` state 배선 — Coordinator에서 View로 제대로 넘어가는지 |
